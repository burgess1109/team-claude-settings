# 把範本變成你們團隊的設定

引導使用者逐區塊處理 `settings/` 底下的內容。

## 開場時先講清楚一件事

**刪除比填寫重要。**

範本最大的陷阱是使用者捨不得刪，最後留下一堆用不到的內容——而 `settings/CLAUDE.md` 每次
session 都會載入，`rules/` 碰到對應檔案就載入。留著沒用的東西是**全團隊每天在付的錢**。

所以每個區塊都要明確提供「**這個我們用不到，刪掉**」這個選項，而且要主動建議刪，
不要預設使用者什麼都想要。

## 步驟 1：團隊基本資訊 → `settings/CLAUDE.md`

一次問完，不要逐格詢問：

| 要問的 | 對應區塊 |
|---|---|
| 跟 AI 對談用什麼語言？commit message 呢？ | 語言 |
| 有沒有既有的 commit / 分支規範？ | Commit 與分支 |
| **團隊用哪個通訊平台？主要通知頻道／群組叫什麼、ID 多少？** | 通訊與工作管理平台 |
| **用哪個工作管理平台？** | 同上 |
| 有哪些環境？各自的寫入門檻？ | 環境對照 |

「需要人類確認才能執行的操作」那張表**預設保留**，它對任何團隊都適用。
只在使用者明確表示要調整時才改。

> 通訊平台的答案**後面步驟 4 會用到**，記下來。

## 步驟 2：架構事實 → `settings/.claude/rules/infra-facts.md`

這是最有價值也最容易填錯的一份。**先講清楚它要收什麼**：

> 不是「我們的架構長什麼樣」，而是「**AI 的預設答案在哪裡會出錯**」。
> 跟社群主流一致的東西一律不寫。

然後問這四題（一次問完）：

1. 線上有哪些服務是「**相容版**」而不是原版？
2. 有哪些技術選型，**社群主流跟你們用的不一樣**？
3. 有哪些東西**本機跑得起來、線上不支援**？
4. 有哪些平台有**自己的工作流程或護欄**，會反過來限制設計？

四題都答不出來時，**建議整份刪除**，不要留一個空框架——空框架會讓後來的人以為已經盤點過了。

填寫時套用 repo 根目錄 `CLAUDE.md`「怎麼盤點架構事實」那節的五條紀律，
特別是「不是真的 X」這句否定句一定要寫進去。

`paths` 也要依實際專案調整——涵蓋產出物不只來源。

## 步驟 3：測試慣例 → `settings/.claude/rules/testing.md`

問兩件事：

1. 主要語言是什麼？→ 調整 `paths` 的檔案 pattern
2. 有沒有跟預設不同的測試慣例？

沒有特殊慣例就**建議刪除整份**——通用的測試建議 AI 本來就會，寫了只是浪費。

## 步驟 4：範例 skill 的去留

`settings/.claude/skills/` 底下每一個都逐一問：**保留改寫 / 直接刪除**。

- `mr-create`（GitLab／`glab`）與 `pr-create`（GitHub／`gh`）— 需要調整 git host、工作管理平台、通知平台。
  **團隊只用其中一個平台就把另一份刪掉**，不要兩份都留
- `create-tag` — 需要確認版號規則（範本假設 semver patch +1）

沒有對應流程就刪掉。**留著一個從沒被叫用的 skill，它的 description 仍然佔著 context**。

保留的話提醒兩件事：
- 內容裡的 `<...>` 要換掉
- 各自的 `NOTES.md` 是給維護者的說明，**不要從 `SKILL.md` 連結它**，也可以直接刪

### 通知區塊要「重寫」，不是「替換」

`mr-create` 與 `pr-create` 步驟 9 各有一塊標了 `⚠️ 由 /onboard 依團隊實際平台改寫`。
那裡**不能只把尖括號換掉**——各平台的訊息語法根本不同，要整段重寫。

依步驟 1 問到的通訊平台，把該平台的實際規則寫死進去：

| 要寫進去的 | 為什麼不能靠 AI 臨場回想 |
|---|---|
| 連結語法 | Slack 是 `<url\|文字>`，Telegram 是 `[文字](url)`，完全不同 |
| Emoji 處理 | Slack 走 API 不解析 `:shortcode:`，必須送 Unicode |
| 特殊字元跳脫 | Telegram MarkdownV2 要跳脫 `.` `-` `!` `(` `)` 等，**漏跳脫整則發送失敗** |
| 單則長度上限 | 超過會被截斷或退回，例如 Discord 2000 字 |
| 目標識別方式 | Slack channel ID `C0...`、Telegram chat_id `-100...`、Discord webhook URL |

**這些細節正是這份 skill 存在的理由。** 只寫「發到 Telegram」而把格式留給 AI 猜，
等於把最容易出錯的部分交回給它——而且錯的時候通常是訊息發不出去或格式爛掉，不會有人回報。

如果使用者不確定自己平台的規則，**明講你不確定，請他查官方文件確認後再填**，
不要憑印象寫進去。寫錯的規則比沒有規則更糟。

## 步驟 5：收尾

1. **驗收佔位符**：重新掃一次 `settings/`，列出還沒替換的 `<...>`。有殘留就明確告知，不要含糊帶過
2. **更新 `README.md` 的「有哪些 skill 可用」表**：依步驟 4 的結果增刪列，改過名稱與觸發方式的也要同步。
   這是**唯一**該動 `settings/` 以外檔案的地方——那張表是成員的入口，跟實際不符時沒有任何錯誤訊息
3. **提醒改 git remote**：這份是從範本 clone 來的，要指向團隊自己的 repo
4. **提示啟用方式**：把下面這段加進 `~/.zshrc`（路徑用實際的絕對路徑填好）

   ```bash
   function claude() {
       CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 \
       command claude --add-dir "<REPO_PATH>/settings" "$@"
   }
   ```

5. **提示驗證**：重開 `claude`，用 `/context` 確認團隊 `CLAUDE.md` 有載入，`/` 選單看得到保留的 skill

## 貫穿全程的規則

以下規則在整個流程中持續有效：

- **每個區塊都要提供「刪除」選項，而且主動建議刪。** 使用者說「先留著好了」時，
  提醒他這是每次 session 的固定成本
- **修改檔案前先顯示要改成什麼**，不要直接寫入。這是使用者的團隊設定，不是暫存檔
- 不要動 `settings/` 以外的檔案，**唯一例外是 `README.md` 的「有哪些 skill 可用」表**（見步驟 5）。
  repo 根目錄的 `CLAUDE.md` 與 `README.md` 其餘部分屬於範本本身，使用者要不要改是另一件事
- 使用者中途離開也沒關係，這個流程可以分次做完——每個步驟結束時說明目前進度
